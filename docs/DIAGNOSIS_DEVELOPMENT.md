# 診断追加の開発フロー

枕・掃除機・ドライヤーの3診断で使った手順を、4つ目以降の診断にそのまま使える形にまとめたものです。
ジャンル固有の情報をテンプレートに埋めていけば、同じ品質基準で診断を追加できます。

- 仕様書テンプレート：[templates/diagnosis-spec-template.md](templates/diagnosis-spec-template.md)
- 採点基準テンプレート：[templates/scoring-criteria-template.md](templates/scoring-criteria-template.md)
- 商品評価テンプレート：[templates/product-evaluation-template.md](templates/product-evaluation-template.md)

実例：`src/data/diagnoses/vacuum.ts`（適格条件・予算上限あり）、`src/data/diagnoses/hairDryer.ts`（予算上限あり）、`src/data/diagnoses/pillow.ts`（従来方式）。

---

## 絶対ルール

どの Phase でも、次のルールを守ります。

1. **商品の順位分布を整える目的で評価値を変更しない。** 1位が偏っていても、評価値ではなく「商品の選び方」や「質問設計の欠陥」として検討する。
2. **性能評価の根拠は、メーカー公式ページ・公式仕様表・取扱説明書を優先する。**
3. **楽天レビュー・レビュー件数・販売店の商品説明は、性能評価の主根拠にしない。**（商品の特定・価格・在庫・画像の確認には使ってよい）
4. **公式情報が不足する項目は、原則として中立値（3）にする。** 「記載を見つけられなかった」ことは「機能が無い」ことの証明にならない。
5. **商品を見る前に採点基準（scoring-criteria.md）を固定する。** 基準を変える場合は、理由・日付・影響を記録し、全商品を同じ基準で採点し直す。
6. **測定条件が違う数値を安易に直接比較しない。**（例：ドライヤーの風量は JIS 測定と自社基準で3倍以上違う。掃除機の重量は本体のみ／使用時で違う）
7. **1位にならない商品があっても、それだけでは除外しない。** 役割の重複・公式情報の不足・販売状況など、別の理由で判断する。
8. **同一商品・型番違い・セット違い・カラー違いを混同しない。** 複数の型番を1ページで売っている楽天出品は使わない。
9. **公開直前に、価格・在庫・画像を再確認する。**（セール終了・在庫処分・価格帯の境界に特に注意）

## Phase 1　診断対象・除外対象の定義

- 何を選ぶ診断かを1文で書く（例：「家庭の床掃除に使うメイン掃除機」）。
- 対象外を明記する（例：ロボット掃除機・ハンディ掃除機、業務用ドライヤー・ペット用など）。
- 対象外は、楽天検索の除外ワードと、候補を絞る基準にも使う。

**成果物：** 仕様書テンプレートの「診断対象・除外対象」

## Phase 2　質問設計

- **質問数：** 原則5〜6問。
- **回答数：** 1問あたり3〜5個。全回答パターン数（各質問の回答数の積）を計算しておく。目安は数百〜3,000程度（`npm run check` で全パターンを実行するため）。
- **Q1：** 一番重視すること（最重要条件）にし、最も重い重みを付ける。
- **予算：** `budgetQuestion()` で作る（選択肢IDは `b1`〜`bN`・`any` で固定）。
- **「採点しない」回答：** 「特にこだわらない」「特にない」は `effects: []` にする。
- **公式情報で差が付かない評価軸を参照する質問は作らない。** ドライヤーでは、静音性（dBを公表する商品がほぼない）を参照する質問が機能しなかったため、「まとまり・仕上がり」に置き換えた。

**成果物：** 仕様書テンプレートの Q1〜Q6

## Phase 3　評価軸・重み設計

- 評価軸（attributes）は **1〜5 の数値**、または条件に使う `true/false` にする。
- **重複する評価軸は統合する。**（例：ドライヤーの damageCare を hairCare に、longHair・quickUse を dryingPower に統合）
- 公式仕様から判定できない評価軸は作らない。
- 各回答が参照する評価軸と求める水準（例：`atLeast 4`）を表にする。
- 重み：Q1 が最大。予算は 15〜20 程度。目安は合計 90〜100。

**成果物：** 仕様書テンプレートの「評価軸」「各回答が参照する評価軸」「重み」

## Phase 4　仮商品による全パターン検証

- 役割の違う仮商品を 6〜8 件作る（`sample: true`、楽天URL・画像は空）。
- 診断ファイルは `enabled: false` のまま、`src/data/diagnoses/index.ts` に登録する。
- `npm run check` と、下記の「シミュレーションチェックリスト」で全パターンを確認する。
- ここで見るのは**質問設計の欠陥**（ある回答が何も区別しない、特定の回答で必ず60%未満になる、など）。仮商品の分布を整える必要はない。

## Phase 5　実商品を見る前に scoring-criteria を固定

- `data/rakuten-candidates/<診断ID>/scoring-criteria.md` を採点基準テンプレートから作る。
- 評価軸ごとに、1〜5 の判定基準・優先する公式情報・測定条件・不明時の扱い・4/5 に必要な根拠を決める。
- **この時点で候補商品の公式仕様を調べない。** 固定後に基準を変えた場合は、版（v1.1 など）・理由・日付を記録する。

## Phase 6　楽天API候補取得

- `scripts/rakuten/presets.ts` にプリセットを追加する。
  - キーワードは役割別（速乾・軽量など）と価格帯別に分け、メーカー名は入れない。
  - 価格帯を指定した検索は `{ keyword, minPrice, maxPrice }` で書ける。
  - `maxPerShop` でメーカー公式店への偏りを防ぐ。`attributeKeys` に評価軸を並べる。
  - 除外ワード（`ngKeyword`）は強すぎると必要な商品まで消える（例：「ストレート」でテスコム TD913A が検索に出なかった）。
- `npm run rakuten:search -- <診断ID>` を実行する。結果は `data/rakuten-candidates/<診断ID>/`（gitignore 対象）に保存される。
- 型番を指定した追加検索は `--keyword "メーカー 型番"` で行う。
- 除外件数と理由、重複統合件数を記録し、8〜12機種程度の候補リスト（shortlist.json）を作る。

## Phase 7　メーカー公式情報による評価

- 候補ごとに、公式製品ページ・仕様表・取扱説明書（PDF）を確認し、商品評価テンプレートに記録する。
- 正確な型番、カラー違い・セット違い・派生モデルの違いを確定する。
- 公式情報を十分に確認できない商品は、推測で採点しない。中立値で無理に残さず「要検討」とする。
- 評価記録は `evaluation-draft.json` に保存する（評価値・根拠・測定条件・公式URL・楽天URL・注意事項）。

## Phase 8　最終8〜10商品程度へ絞り込み

- 判断材料：公式情報の確実さ、役割の重複、価格帯のカバー、販売状況、メーカーの偏り。
- 各価格帯をカバーする（特に最安の価格帯は、最低3機種を目標にする）。
- 本番に入れない商品も、評価記録には「予備」「除外（理由）」として残す。

## Phase 9　実商品を使った全パターン検証

- `hairDryer.ts` などは変更せず、評価案の商品で全パターンを計算する（シミュレーションチェックリスト）。
- 結果は `data/rakuten-candidates/<診断ID>/simulation-*.txt` に保存する。
- 気になる結果があっても評価値は変えない。変えてよいのは、商品の選び方・質問設計（理由を記録）・採点基準の明らかな欠陥（版を上げて全商品を採点し直す）。

## Phase 10　本番データ投入

- 評価記録から診断ファイルへ転記する（手作業での転記ミスを防ぐため、スクリプトで生成するとよい）。
- 商品文章（説明・特徴・良い点・気になる点・向いている人・注意書き）は公式仕様に基づく中立的な表現にする。販売店の宣伝文句や楽天レビューを性能の事実として書かない。
- `caution` に、想定するカラー・構成・セット、価格が変わりやすい点を書く。
- 楽天URLは `hb.afl.rakuten.co.jp` のアフィリエイトURLを使う（`rafcid` を含めない）。
- 画像に販促文字（「ポイント10倍」「◯%OFF」など）が目立つ場合は、同じ商品ページ内の別の画像にする。
- 本番ファイルでの全パターン結果が、Phase 9 のシミュレーションと一致することを確認する。

## Phase 11　SEO・画面・レスポンシブ確認

- `seo.title`・`seo.description`・`intro`・`guide`（選び方）を、診断対象と判断材料が自然に分かる文章にする。
- 画面確認は、一時的に `enabled: true` にして開発サーバーで行い、終わったら必ず元に戻す（バックアップとハッシュで照合）。
- 320 / 390 / 768 / 1280px で、診断開始・全問回答・結果TOP3・画像・楽天ボタン・横スクロールなし・JSエラーなしを確認する。

## Phase 12　既存公開診断の完全互換性確認

- 公開中の全診断について、全回答パターンの順位・相性%・スコア・理由・別枠・ラベルが、公開中のコミットと完全に一致することを確認する。
  - 方法：`git archive HEAD src` で公開中のコードを一時フォルダに展開し、同じ回答で両方の `runDiagnosis` を実行して比較する。
- 共通エンジンを変更した場合は、特に念入りに確認する。

## Phase 13　enabled:true → sitemap → commit → push → 本番確認

公開ワークフロー（`scripts/publishDiagnosis.ts`）で自動実行する。手順の中身は README「診断を公開する手順」を参照。

```bash
npm run publish:diagnosis -- <診断ID> --dry-run   # 確認だけ
npm run publish:diagnosis -- <診断ID> --message "Publish <ID> diagnosis with N real products"
```

- 1つでも失敗したら停止し、commit・push しない（enabled を書き換えていれば元に戻す）。
- 公開工程で変えるのは `enabled: false` → `true` の1行だけ。採点・質問・商品を直した場合は、公開ワークフローの前に Phase 9〜12 をやり直す。
- 公開済みの診断を後から確かめるときは `--verify`（本番確認まで行い、ファイルは変更しない）。
- 検証範囲は変更内容から自動判定される（対象診断のみ／変更された診断のみ／全診断）。共通の計算部分や判定できない変更があれば全診断をフル検証する（README「検証範囲の自動判定」）。
- dry-run 成功後、ファイルを変えずに公開すれば重い検証は再利用される。dry-run 後に何か直した場合は自動で再検証になる。
- 自動化していない確認（楽天ページの型番・カラー・セット構成、セール終了日、画像の販促文字）は、公開前に人が行う。

## 共通エンジンの使い方

### 「単なる好み」と「絶対条件・上限条件」を分ける

| 種類 | 例 | 使う仕組み | 結果への影響 |
|---|---|---|---|
| 単なる好み | 軽いほうがいい、速く乾かしたい | `effects`（`atLeast` など） | 相性%が上下するだけ。条件に合わない商品も上位に来うる |
| 絶対条件 | コードレスでないと困る | 選択肢の `eligibility` | 条件を満たす商品だけが通常ランキングに入る |
| 上限条件 | 予算を超えたくない | `budgetQuestion({ asLimit: true })`（`maxPriceRange`） | 予算内の商品だけが通常ランキングに入る |

判断の目安：**「条件を満たさない商品が1位に出たら、ユーザーが不満に感じるか」**。感じるなら絶対条件・上限条件、多少なら許容できるなら好み（effects）にする。

### 各機能の判断基準

| 機能 | 使う場面 | 注意 |
|---|---|---|
| `enabled` | 診断ごとの公開・準備中の切り替え。`false` の間はトップで「準備中」、ページは noindex、sitemap に載らない | 開発中は必ず `false`。公開は Phase 13 でだけ `true` にする |
| `budgetQuestion()` | 予算の質問は常にこれで作る | 選択肢IDは `b1`〜`bN`・`any` で固定。`noLimitLabel` は「上限なし」の意味で、価格では採点しない |
| `maxPriceRange` | 予算を上限条件にしたいとき。`budgetQuestion({ asLimit: true })` で自動設定される | 最安の価格帯の商品が3件未満だと、その予算では常に別枠が出る |
| `eligibility` | 絶対条件（例：`cordless: true`）。`notice`（結果上部の説明）と `supplementLabel`（補完時のラベル）も書ける。複数条件をすべて満たす商品に限る場合は配列で書く（例：フライパンの「ガス火・IHどちらでも」＝`[gasOk: true, ihOk: true]`） | その選択肢の `effects` は空にする（全候補が条件を満たすので採点しても差が付かない）。予算より優先される。条件を満たす商品が全体で3件未満だと、条件外の商品が別枠に入るため、条件ごとに対応商品を3件以上そろえる |
| `scoring.tieBreak` | 実商品を入れる診断では基本的に `true` | 完全同点のときだけ、質問の一致度 → 回答に関係する評価値 → 商品ID の順で並べる。価格・レビュー数・メーカー名は使わない |
| `scoring.lowMatchNotice` | 条件をすべて満たす商品が少ない回答の組み合わせがあり、1位の相性が60%未満になるパターンが残る診断 | 1位が60%未満のときだけ結果上部に説明を出す。60%未満を減らすための点数調整の代わりに使う（採点・順位・相性%は変わらない） |
| `supplements` | 通常ランキングが3件未満のときだけ、条件外の商品を別枠に表示する（エンジンが自動で作る） | 別枠は順位を付けず「参考相性」と表示。通常ランキングより%が高く見えることがあるが、別枠なので問題ない |
| `overBudget` | 別枠の商品が予算を超えている印 | ラベル「予算を少し超えます」 |
| `ineligible` | 別枠の商品が適格条件を満たさない印 | ラベルは `supplementLabel` |
| `notices` | 選んだ適格条件の `notice` が入る | 結果の上部に表示される |

並び順は「条件を満たす → 予算超え → 適格条件外 → 両方外」で、各グループ内は相性の高い順です。

## シミュレーションチェックリスト

Phase 4（仮商品）と Phase 9（実商品）で、全回答パターンについて確認します。

- [ ] 結果なし（表示が3件未満）：0件
- [ ] 1位（トップ）の相性60%未満：件数と、どの回答で起きるか
- [ ] 商品別の 1位 / 2位 / 3位 / TOP3 の回数
- [ ] 最大1位率
- [ ] 1位にならない商品
- [ ] TOP3に入らない商品
- [ ] Q1 の回答ごとの1位の商品と相性（最小・中央）
- [ ] 予算帯ごとの1位の商品と相性、別枠の発動件数
- [ ] eligibility 違反（通常ランキング・別枠に適格条件外が不正に入っていない）：0件
- [ ] maxPriceRange 違反（通常ランキングに予算超え）：0件
- [ ] 予算内の商品があるのに1位が予算超え：0件
- [ ] supplements：通常ランキングが3件あるのに別枠が出る 0件、条件を満たす商品が別枠に入る 0件
- [ ] 理由文の矛盾（理由に挙げた回答の一致度が低い、など）：0件
- [ ] 通常ランキング内の相性%の逆転：0件
- [ ] tieBreak の件数（1位と2位の完全同点）と決着方法の内訳
- [ ] ID順まで到達した件数とペア

> **このチェックリストは、分布を均等にするための評価調整には使いません。**
> 偏りや1位にならない商品が見つかった場合は、商品の選び方・質問設計・採点基準の欠陥として検討し、評価値そのものは変えません。

`npm run check` は、このうち「結果なし」「予算・条件違反」「%逆転」「別枠の条件」を全診断で自動確認します。

## これまでの診断で得た注意点

| 事例 | 教訓 |
|---|---|
| ダイソン SV50 FC の質量を、別機種（SV50 FF）の値で採点していた | 検索結果の要約をうのみにせず、公式ページを実際に開いて型番と数値を確認する |
| Shark CS851J がセール価格で価格帯3、終了後は4 | セール期間と通常価格を記録し、公開直前に再確認する |
| ドライヤーの風量が JIS と自社基準で3倍以上違った | 測定条件が明記された値だけを比較する（基準 v1.1） |
| KINUJO の代表出品が複数機種の混在ページだった | 単独型番の出品を使う |
| 楽天APIの URL に `rafcid`（アプリID入り）が含まれていた | 取り込みツールで除去済み。手でURLを貼るときも確認する |
| 静音性を公表する商品がなく、質問が機能しなかった | 公式情報で差が付かない評価軸を質問で参照しない |
| テスコム TD713A が在庫処分特価だった | 在庫処分・終売の可能性がある商品は、分布への影響も含めて慎重に判断する |
